## 1. Executive Summary & Purpose

This document provides the definitive markdown representation and architectural alignment of the updated 18-test UVM testplan (`UVM_Testplan_RISC-V_Network_Telemetry_SoC_Updated.xlsx`).

While the master verification plan (`doc/UVM_Verification_Plan.md`) outlines the layered environment, bringup services, and C-SV handshakes, this 18-test matrix establishes the **concrete, actionable signal-level checkpoints, SystemVerilog/UVM working principles, and C firmware working principles** for every deliverable test.

### Functional Domains Covered:
1. **Infrastructure & Reset** (Tests 1–2): Reset sequencing, mid-traffic reset assertion, protocol recovery.
2. **AHB-Lite Interconnect** (Tests 3–5): Address decode, dual-master arbitration, wait-states, pipelining.
3. **AXI-Lite & Bridge** (Tests 6–9): Address handshakes, byte-lane strobes (WSTRB), bursts, error handling.
4. **UART Peripheral** (Tests 10–12): Baud rate generation, framing, transmission/reception, status/interrupts.
5. **AES-128 Accelerator** (Tests 13–14): NIST vector encryption, register readback, polling vs IRQ completion.
6. **SoC Integration & Stress** (Tests 15–18): Concurrency, firmware boot, monitor tokens, recovery from fault injection.

## 2. Master 18-Test Verification Matrix

| ID | Test Name | Scope & Description | Checkpoints (Signal-Level PASS/FAIL) | SystemVerilog / UVM Working Principle | C Firmware Working Principle |
|---|---|---|---|---|---|
| **1** | **Basic Setup and Reset** | Confirm the testbench starts, all reset domains reach their inactive state, and the SoC enters a known idle condition before traffic begins. | 1) Observe clock toggling and reset assertion/deassertion (`reset_n`).<br>2) After reset release, check bus select/valid signals are low, ready signals reach their idle value, interrupt outputs (`uart_irq_o`, `aes_irq_o`) are inactive, and no bus X/Z values remain.<br>3) **PASS:** Reset timing matches design spec and design stays idle without UVM errors; **FAIL:** Unknowns, stuck controls, or unexpected activity. | SV/UVM generates clock and reset, waits for reset release, samples interface signals, and asserts known reset/idle values. A monitor records any unexpected bus or interrupt activity. | C test is not required for standalone reset verification. Startup code may wait for reset release and write a known value to a safe status register; SV still checks reset and bus signals. |
| **2** | **Reset During Activity** | Check that an in-progress bus transaction or UART transfer is safely interrupted by reset and that the design returns to a usable state. | 1) Start an AHB/AXI transfer or UART transmit.<br>2) Assert reset while `HTRANS` indicates a transfer, `HREADY` is low, AXI `VALID` is high, or UART TX is active.<br>3) Check reset clears/returns control signals to reset values and no stale `VALID`/`SELECT` remains asserted after release.<br>4) Start a new transfer and confirm it completes with expected response/data.<br>5) **PASS:** Clean restart occurs; **FAIL:** Deadlock, stale activity, or incorrect post-reset data appears. | SV sequence starts traffic and asserts reset at a controlled point; monitors check reset values, protocol recovery, and completion of a fresh transaction. Scoreboard discards or marks pre-reset transactions according to design spec. | If software reset is supported, C writes documented reset-control register and waits for ready/status bit. SV monitors reset output and bus recovery. Do not use C for a hardware-reset-only scenario. |
| **3** | **AHB Address and Access Checks** | Verify that valid AHB-Lite addresses reach the intended target, reads/writes preserve data, and unmapped addresses return the specified error response. | 1) Drive `HSEL`/`HTRANS=NONSEQ` with `HADDR`, `HWRITE`, `HSIZE` and `HWDATA` for a legal access; check `HREADY` and `HRESP`.<br>2) Read back using `HADDR` and `HWRITE=0`; compare `HRDATA` with written/expected data.<br>3) Access first/last address of each mapped region and one unmapped address.<br>4) **PASS:** Mapped accesses complete with `HRESP=OKAY` (0) and correct `HRDATA`; unmapped access returns specified `ERROR` (1) response without corrupting a valid target; **FAIL:** Wrong target/data/response or hang. | SV/UVM driver drives AHB signals; monitor captures address/control/data/response; scoreboard compares expected decode target and read data. Illegal address is deliberately injected by the sequence. | C firmware writes/reads memory-mapped registers using volatile pointers and checks returned values. For unmapped-address testing, use platform-approved fault handler; SV bus-level test is preferred because illegal C load/store traps the CPU. |
| **4** | **AHB Traffic and Arbitration** | Check that instruction-side and data-side requests both make progress when active together and that the arbiter does not lose or duplicate transfers. | 1) Generate simultaneous requests and observe request/grant signals, `HADDR`, `HTRANS` and `HREADY`.<br>2) Check each granted request is followed by the expected transfer and response.<br>3) Count accepted transfers at handshake point (`HTRANS` valid and `HREADY=1`); compare issued vs completed counts.<br>4) **PASS:** Both requesters complete within design’s arbitration expectations and data/order are correct; **FAIL:** Starvation beyond specified limit, duplicate/lost transfer, or data mismatch. | SV sequences create overlapping requester traffic with unique addresses/data. Monitors track request/grant and AHB acceptance; scoreboard checks completion counts and expected arbitration behavior. | C firmware can create concurrent instruction fetches and data loads/stores, but cannot reliably control exact simultaneous bus requests. SV/UVM is the primary test for arbitration timing; C provides a system-level workload. |
| **5** | **AHB Wait States and Back-to-Back Transfers** | Verify the master and target hold transaction information stable during wait states and handle consecutive transfers without gaps causing data loss. | 1) Hold `HREADY` low for several cycles during a transfer.<br>2) While stalled, check `HADDR`, `HTRANS`, `HWRITE` and `HWDATA` remain unchanged until accepted.<br>3) Drive back-to-back transfers across consecutive cycles (`NONSEQ` followed by `SEQ`/`NONSEQ`) and verify each addresses the correct target with expected response.<br>4) **PASS:** Signals remain stable during wait states, handshakes complete normally upon release, and back-to-back beats complete without dropped beats; **FAIL:** Dropped/corrupted data or premature change. | SV driver controls wait-state insertion and drives pipelined back-to-back transfers. Monitor verifies stability rules and beat-to-beat continuity. Scoreboard checks all beats match expected sequence items. | C test can perform burst/consecutive loads and stores in a loop to create back-to-back traffic. C cannot directly force slave wait states; SV testbench handles wait-state injection. |
| **6** | **AXI Address and Handshake Checks** | Verify that read and write transactions follow standard valid/ready handshake rules and reach the intended peripheral target. | 1) Issue write address/data (`AWVALID`/`WVALID`) and read address (`ARVALID`).<br>2) Observe `AWREADY`, `WREADY`, `BVALID`, `BREADY`, `ARREADY`, `RVALID` and `RREADY`.<br>3) Check control and data signals stay stable from `VALID` assertion until `READY` is high.<br>4) Confirm write completes with `BRESP=OKAY` and read returns expected data with `RRESP=OKAY`.<br>5) **PASS:** Handshakes follow protocol, responses are valid, and read data matches; **FAIL:** Premature signal drop, missed handshake, invalid response or wrong read data. | SV/UVM sequence drives address and data channels with varying delays; monitor samples handshakes and enforces AXI protocol assertions. Scoreboard compares read data against written values. | C firmware performs memory-mapped writes and reads to peripheral registers. C confirms functional write/read completion, while SV checks low-level channel handshakes. |
| **7** | **AXI Write Strobe and Byte-Lane Checks** | Confirm byte, half-word and full-word writes update only the targeted byte lanes and unselected lanes remain unchanged. | 1) Write known initial data across a 32-bit/64-bit location.<br>2) Issue writes with specific `WSTRB` patterns (e.g. single byte `0x1`, `0x2`, `0x4`, `0x8` or half-word `0x3`, `0xC`).<br>3) Read back full word/location; check only addressed bytes changed.<br>4) **PASS:** Targeted byte lanes reflect new data and unaddressed bytes retain original values; **FAIL:** Overwritten neighboring bytes, wrong lane updated, or write ignored. *(Validates M4a `ahb_to_axi_bridge` word-lane fix)*. | SV sequence generates directed transactions with specific addresses, sizes and strobe patterns. Monitor logs transactions and scoreboard performs masked byte-level comparisons. | C firmware writes using `uint8_t*`, `uint16_t*` and `uint32_t*` pointers to check byte/half-word writes. Software reads back 32-bit words to verify correct lane positioning. |
| **8** | **AXI Burst and Outstanding Transfers** | Verify that multi-beat transfers advance addresses correctly and that multiple outstanding transactions complete in the specified order without corruption. | 1) Issue fixed/incrementing bursts and observe `ARLEN`/`AWLEN`, `ARSIZE`/`AWSIZE`, `ARBURST`/`AWBURST` and beat addresses.<br>2) For outstanding transactions, track IDs (`AWID`, `BID`, `ARID`, `RID`) and handshake progress.<br>3) Check each beat completes with `RLAST`/`WLAST` asserted on final beat.<br>4) **PASS:** All beats complete, addresses increment as specified, `LAST` indicators align with programmed length, and data order is preserved; **FAIL:** Wrong beat count, out-of-order data, or missing `LAST`. | SV/UVM sequencer issues burst items and pipeline sequences; monitor reassembles burst beats into complete transactions; scoreboard verifies beat ordering and address progression. | C firmware can generate sequential multi-word operations using `memcpy` or block loops. Low-level AXI burst generation depends on CPU LSU capability; SV provides full burst control. |
| **9** | **AXI Error Handling** | Check that invalid addresses, unsupported access sizes or peripheral error conditions return `DECERR` or `SLVERR` and the bus recovers cleanly. | 1) Issue access to an unmapped AXI address or assert an unsupported size/control combination.<br>2) Observe `RRESP` or `BRESP` for `SLVERR` (`2'b10`) or `DECERR` (`2'b11`).<br>3) Confirm transfer completes cleanly through normal handshake and no channel hangs.<br>4) Follow with a valid transfer to verify bus is operational.<br>5) **PASS:** Documented error response is observed, handshakes complete without hang, and subsequent valid transfer succeeds; **FAIL:** Bus deadlock, silent drop without error, or corrupted subsequent access. | SV sequence injects targeted invalid addresses and monitors response channels. Scoreboard checks error status and verifies subsequent normal transaction passes. | C firmware can attempt to access unmapped peripheral offsets if CPU fault handler can intercept the bus error. If an access causes unrecoverable CPU exception, use SV testbench instead. |
| **10** | **UART Basic Transmission** | Verify that writing data to the UART transmit register produces properly framed serial output matching the programmed format. | 1) Program UART format (start bit, 8 data bits, stop bit).<br>2) Write known byte into TX data register.<br>3) Sample `uart_tx_o` pin; verify start bit (low), bit sequence (LSB to MSB), parity (if enabled) and stop bit (high).<br>4) Measure bit timing against expected baud period.<br>5) **PASS:** Serial waveform matches expected frame and bit timing within tolerance; TX empty/ready status updates correctly; **FAIL:** Incorrect frame format, inverted data, framing error, or timing violation. | SV sequence writes TX register via bus agent; a passive UART monitor on `uart_tx_o` samples the pin, deserializes the byte, and sends it to the scoreboard for bit-level and character comparison. | C firmware initializes UART and writes characters to the TX register. C checks TX empty status bit before and after write; SV verifies physical pin waveform and timing. |
| **11** | **UART Reception and Framing** | Verify that serial data driven into the receiver is correctly deserialized into the receive buffer and framing errors are detected. *(Prepared for full RX integration)*. | 1) Drive valid serial frame into `uart_rx_i` with matching baud rate.<br>2) Read RX data register; check received byte matches driven value.<br>3) Drive frame with intentional framing error (e.g. missing stop bit) and observe error flag in status register.<br>4) **PASS:** Valid data is read back correctly; status register flags data-ready and framing error under test conditions; **FAIL:** Corrupted receive byte, missed flag, or deadlock. | SV UART VIP driver drives serial frames onto `uart_rx_i`. Bus monitor checks CPU read from RX register. Scoreboard compares driven character against read character and status flags. | C firmware polls RX ready status bit, reads received byte, and compares against expected pattern. C also reads status register to check error flags when error injection is active. |
| **12** | **UART Baud Rate and Configuration** | Confirm changing the baud divisor correctly alters the serial bit period and modifying frame parameters updates the frame length. | 1) Configure divisor for baud rate A; transmit a byte and measure bit period on `uart_tx_o`.<br>2) Reconfigure divisor for baud rate B; transmit a byte and measure new bit period.<br>3) Check ratio of measured bit periods matches ratio of divisor settings within tolerance.<br>4) **PASS:** Measured bit times match calculated periods for both rates; **FAIL:** Baud rate does not change, timing error exceeds tolerance, or transmission fails after reconfiguration. | SV sequence programs divisor registers, triggers transfers at multiple baud settings, and monitor measures bit widths. Scoreboard calculates expected periods and checks measured values against tolerance limits. | C firmware programs baud divisor registers, transmits known markers at each rate, and checks status. Bit-period measurement is performed by the SV testbench monitor on the serial output pin. |
| **13** | **AES Basic Encryption** | Verify the AES accelerator accepts a key and plaintext, performs encryption, asserts done/ready, and outputs correct ciphertext matching NIST KAT. | 1) Write 128-bit key into `KEY0..KEY3` registers.<br>2) Write 128-bit plaintext into `DATA0..DATA3` registers.<br>3) Write start bit in `CONTROL` register.<br>4) Monitor `STATUS` register and `aes_irq_o` output.<br>5) Once done asserts, read `RESULT0..RESULT3`.<br>6) **PASS:** Ciphertext matches expected NIST vector (`0x70b4c55a d8cdb780 6a7b0430 69c4e0d8`), busy/done flags follow documented sequence, and `aes_irq_o` asserts; **FAIL:** Ciphertext mismatch, hang in busy state, or missing completion indicator. | SV sequence drives key/data writes, triggers encryption, polls or waits for interrupt, reads result registers, and scoreboard compares ciphertext against reference model or NIST vector. | C firmware writes key and plaintext using memory-mapped register writes, initiates encryption, polls status register until done, reads result words, and checks against expected ciphertext. |
| **14** | **AES Key and Data Loading** | Check that key and data registers accept writes, support readback, and retain values without unintended corruption during operation. | 1) Write unique test patterns into key registers; read back and compare.<br>2) Write unique test patterns into data input registers; read back and compare.<br>3) Trigger encryption; check key and input registers remain intact or follow documented update rules.<br>4) Clear done flag and verify status register returns to ready state.<br>5) **PASS:** All registers accept and return correct data; no bits are stuck; status clear works as specified; **FAIL:** Readback mismatch, unintended register clearing, or stuck status bit. | SV sequence tests register read/write patterns, bit walk, and status/control register semantics. Monitor samples bus and peripheral control/status/IRQ signals. Assertions check busy/done ordering; scoreboard checks register access and interrupt clear behavior. | C firmware configures interrupt enable, starts AES, services or polls completion, reads output and clears status using documented semantics. SV observes the actual IRQ pin and verifies timing independently of software. |
| **15** | **SoC Memory and UART Integration** | Check that processor/firmware memory accesses and UART operation work together through the integrated address map and bus fabric. | 1) Run memory test with known patterns; observe instruction/data bus transactions and compare readback.<br>2) Configure UART through mapped registers (`0x1000_0000`) and transmit known byte stream.<br>3) Check bus responses, memory contents, UART TX frame and interrupt/status behavior.<br>4) **PASS:** Memory data is preserved, UART output decodes correctly (`UART_CHECK_RESULT: PASS`), and all transactions complete without unexpected errors; **FAIL:** Corruption, wrong routing or stalled access. | SV/UVM monitors integrated bus transactions, memory responses and UART pins; scoreboard checks memory patterns and UART frames. Firmware is loaded as CPU stimulus. | C firmware is the primary system-level stimulus: initialize memory, perform read/write checks, configure UART and transmit known data. SV/UVM observes bus and peripheral signals to identify integration failures. |
| **16** | **Multiple Blocks Active Together** | Check that memory traffic and peripheral activity can overlap without lost transactions, corrupted data or unexpected stalls. | 1) Run memory reads/writes while UART transfers and AES operation are active simultaneously.<br>2) Observe AHB/AXI `VALID`/`READY` or `HTRANS`/`HREADY` handshakes, response signals, UART TX, and AES busy/done/IRQ.<br>3) Compare all memory data, UART bytes and AES output against expected values; count accepted and completed bus transactions.<br>4) **PASS:** All operations complete with correct results and no protocol violations; **FAIL:** Lost/duplicated requests, data corruption, deadlock or unexpected errors. | SV/UVM starts concurrent sequences on bus and peripheral agents; monitors collect all activity and scoreboard compares each block’s results. Bounded timeouts detect deadlock. | C firmware runs a combined workload (memory loop, UART transmit, AES operation) and checks return/status values. SV/UVM monitors signals and provides deterministic concurrency and timeout checks. |
| **17** | **Firmware Boot and Monitor Check** | Verify the CPU starts supplied firmware, performs expected initialization and generates the bus/peripheral activity described by the test. | 1) Load firmware into IMEM and release reset; observe CPU fetch addresses and instruction/data bus activity (`ifu_*` and `lsu_*`).<br>2) Check PC/fetch path reaches expected boot region (`0x0000_0000`) and firmware reaches known completion/status marker in DMEM.<br>3) Confirm expected register writes or UART output occur and no bus error/exception appears unexpectedly.<br>4) **PASS:** Firmware reaches success marker (`P2_TB2_RESULT: PASS`), AHB monitor proves activity thresholds (`AHB_RW_MONITOR: PASS`), and monitored transactions match expected sequence; **FAIL:** Timeout, wrong boot address, unexpected error response or missing marker. | SV/UVM loads/starts firmware test, monitors CPU bus transactions and peripheral outputs, and checks completion marker/timeout. Transaction-level scoreboard tracks expected accesses. | C is the test program running on the CPU: initialize blocks, perform intended accesses, and write a PASS/FAIL marker or send a known UART message. Marker is evidence of software progress; SV checks hardware transactions and signals. |
| **18** | **Invalid Accesses and Recovery** | Verify documented error responses for invalid accesses and ensure fabric/peripherals continue operating after the error or a controlled stall. | 1) Issue unmapped access and unsupported size/alignment or invalid byte enables. Observe `HRESP` (AHB default slave 2-cycle ERROR) or AXI `RRESP`/`BRESP` and completion handshakes.<br>2) Check no valid mapped register/memory location is unintentionally modified.<br>3) Follow error with a valid read/write and verify normal operation resumes.<br>4) Optionally apply back-pressure during a valid transaction and release it.<br>5) **PASS:** Specified error is returned, no unrelated data changes, and next valid transaction completes; **FAIL:** Silent error, bus hang, corruption or failure to recover. | SV/UVM injects invalid addresses, unsupported controls and controlled stalls; monitor checks error responses and handshake completion; scoreboard verifies unaffected locations and successful follow-up transaction. | C tests documented error/status paths where platform defines safe recovery. An unmapped CPU access causes an exception, so use registered fault handler or perform in SV. C then issues a valid access to confirm software-visible recovery. |

## 4. Synthesis of Working Principles (SV/UVM vs C Firmware)

The testplan explicitly differentiates the role of **SystemVerilog/UVM** versus **C Firmware**:

1. **When SV/UVM is Primary:**
   - Precise cycle-by-cycle protocol assertions (e.g. `HTRANS` hold time, wait-state stability, address-phase pipeline overlap).
   - Clock and reset sequencing, glitch testing, and mid-burst reset assertion.
   - Non-fatal bus fault injection (deliberate unmapped address access that would trigger a fatal CPU trap if executed from C without a special trap handler).
   - Independent verification of external physical pins (`uart_tx_o` bit timing, baud period calibration, start/stop bit framing).

2. **When C Firmware is Primary:**
   - Real system-level workloads where the VeeR EL2 core executes real instructions from IMEM (`0x0000_0000`).
   - End-to-end data flows (software assembles telemetry, writes AES registers, triggers encryption, polls status, transmits report over UART).
   - Software-visible registers, memory-mapped I/O reads/writes, and mailbox handshakes.
